# Ревизия веб-проекта (read-only)

## Когда использовать

Разобраться в запутанном веб-проекте, когда агент не видит очевидных багов. Срабатывает на «разгреби проект», «Claude/Codex не видит визуальных багов», «сверь с ТЗ/scope», «что в продакшене выглядит странно», «ничего не менять, только проверь». Не срабатывает на создание нового сайта с нуля.


Скилл для случая, когда человеку нужно **вернуть контроль над запутанным проектом**
или когда агент-кодер не замечает очевидных продуктовых/визуальных проблем: сломанный
хедер, дублирующийся текст, забытые демо-маршруты, неверные тексты, скрытое разрастание
объёма, страницы, которые в продакшене выглядят странно, правки не в том файле.

Это в первую очередь **проверка без правок**. Не редактируй проект, пока человек явно
не попросит чинить.

## Когда включаться

- «разгреби проект», «проект вышел из-под контроля»
- «Claude/Codex не видит очевидных визуальных багов»
- сломанный хедер/навигация, дубли текста, странный текст в продакшене
- «сверь с ТЗ / scope»
- «найди, что в проде выглядит странно»
- «ничего не менять»

## Главный принцип

Раздели три роли, которые агенты-кодеры часто путают:

1. **Ревизор объёма** — что должно существовать по ТЗ/роадмапу.
2. **Визуальный/копирайт QA** — что пользователь реально видит в браузере и в тексте
   для доступности.
3. **Картограф владения кодом** — какой маршрут/компонент реально живой, чтобы будущая
   правка попала в нужный файл.

Никогда не прыгай сразу в правки кода. Сначала — доказательства.

## Порядок работы

### 1. Установи режим read-only

- Повтори путь проекта и правило «без изменений без разрешения».
- Если есть ТЗ, роадмап, PDF, бриф или коммерческое предложение — сначала прочитай его.
- Сохрани в заметки только устойчивые факты: путь проекта, путь репозитория, явное
  правило «не править», идентичность проекта (если человек ведёт заметки).

### 2. Пойми форму проекта без правок

Только чтение (файлы/поиск/терминал):

- определи фреймворк и скрипты (`package.json`, конфиги);
- проверь текущую ветку и нетрекнутые файлы;
- перечисли маршруты/компоненты;
- запусти дев-сервер только если нужно и безопасно;
- отметь устаревшие/нетрекнутые каталоги, но ничего не удаляй.

Для путей с кириллицей на Windows заключай путь в кавычки:

```bash
cd 'D:/Проекты/site-123' && git status --short
```

Если инструмент не принимает кириллический рабочий каталог — запусти из нейтрального
каталога и передай путь как аргумент/в кавычках.

### 3. Собери карту владения маршрутами

Таблица:

| URL | Файл маршрута | Основной компонент | Есть в ТЗ? | Статус | Заметки |
|---|---|---|---|---|---|

Это не даёт агенту чинить мёртвые компоненты. В Next.js различай:

- `src/app/<route>/page.tsx` — живой вход в маршрут;
- `src/components/pages/*` — реализации страниц;
- старые/параллельные компоненты, которые сейчас не импортирует ни один маршрут.

### 4. QA через браузер

Для каждого важного для продакшена маршрута:

- открой в браузере;
- сними accessibility-снимок и текст DOM;
- посмотри видимую навигацию/хедер/кнопки;
- проверь десктоп и мобильную ширину, когда возможно;
- зафиксируй ошибки/предупреждения консоли;
- сравни `innerText` с accessibility-снимком, когда анимированный текст разбит на span'ы.

Держи браузерные доказательства ограниченными. Не гоняй тяжёлые vision-вызовы, когда
на вопрос отвечает снимок DOM/accessibility. Если интерактивная консоль браузера
постоянно падает — перестань её мучить и используй установленный в проекте Playwright:
зайди только на нужные маршруты, сними `console` и `pageerror`, выдай компактный объект
состояния (`status`, заголовок, H1, горизонтальный overflow). Десктоп и мобильный контекст
запускай явно.

Важно: страница может выглядеть нормально, но быть сломанной в accessibility/SEO. Анимация
заголовка по словам часто даёт склеенный текст вроде `С2017года` в снимках. Считай это
QA-находкой, а не автоматически багом кода, пока не подтвердишь визуально.

### 5. Проверка объёма и продакшен-поверхности

Классифицируй видимые фичи: **в ТЗ сейчас** / **следующая фаза** / **явно исключено** /
**внутреннее/демо/админ**.

Ищи опасные утечки в продакшен:

- админ/ops/курьерские маршруты;
- фейковые сценарии оплаты;
- обещания трекинга/статусов, исключённые из ТЗ;
- демо-страницы и забытые экспериментальные маршруты;
- дублирующиеся системы навигации.

Если middleware редиректит/404-ит исключённые маршруты — отметь как текущую защиту, но
всё равно укажи код как источник когнитивной нагрузки.

### 6. Бизнес-логика и миграции (когда в объёме)

Для денег, единиц измерения, исторических данных и инициализации БД требуй все три,
прежде чем назвать дефект подтверждённым:

1. **Проследи размерности от начала до конца** — различай нативные и минорные единицы,
   включая payload API, критерий сопоставления, колонки в БД, SQL-вьюхи и форматирование.
2. **Собери крошечный детерминированный repro** — лучше существующий фокусный тест;
   иначе inline-проверка на stdlib/Node вне репозитория. Покажи конкретный вход, факт и
   ожидание. Не создавай файлов проекта в read-only ревизии.
3. **Назови точный путь в коде** — `file:line`, severity, последствие, минимальная
   безопасная рекомендация.

Сверяй дублирующиеся реализации. Корректный калькулятор в приложении не доказывает, что
SQL-вьюха верна; зелёные юнит-тесты могут скрывать противоречивую реализацию в БД.

Для миграций сравни набор SQL-файлов, журнал миграций, снапшоты, скрипты пакета и
задокументированные раннеры. Раздели: статически подтверждённые пробелы workflow /
подтверждённые на живой свежей БД сбои / непроверенные гипотезы, если одноразовой БД нет.

Никогда не используй production-доступ, чтобы закрыть пробел проверки. Не читай явно
исключённые файлы даже для диагностики через git-diff.

### 7. Находки в формате доказательств

```text
[Страница / маршрут или область бизнес-логики]
Severity:
Что не так:
Доказательство и file:line:
Минимальный repro (вход / факт / ожидание):
Минимальная рекомендация:
Статус: подтверждённый дефект / гипотеза / операционный риск
```

Избегай расплывчатого «сделать лучше». Будущим агентам нужны точные файлы и симптомы.
Явно отделяй подтверждённые дефекты от гипотез и операционных рисков.

### 8. Сохрани ревизию

Если человек ведёт заметки по проекту — сохрани карту маршрутов, находки QA, сводку по
объёму и следующие безопасные шаги. Не сохраняй шумные логи команд, если они не нужны
как доказательство.

## Ошибки

- **Не верь ментальной модели агента-кодера.** Проверяй живые маршруты и вывод браузера.
- **Не правь во время ревизии.** Людям часто сначала нужен контроль, а не сюрпризы.
- **Дубли строк в коде — сами по себе не баг.** Многие повторы — это ярлыки и ожидаемый
  словарь UI. Подтверждай видимое дублирование.
- **Не полагайся только на скриншоты.** Проверяй текст DOM, accessibility, консоль,
  импорты маршрутов.
- **Не давай коду будущих фаз отвлечь от объёма запуска.** Помечай его как скрытый/исключённый,
  пока он не протекает в продакшен-UI.
