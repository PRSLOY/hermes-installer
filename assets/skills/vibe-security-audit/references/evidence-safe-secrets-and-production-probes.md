# Секреты и production-проверки без утечки значений

Этот протокол — для случая, когда нужно доказать, что секрет «живой», или сравнить
значения из репозитория с конфигурацией деплоя, не раскрывая сами данные.

## Подтверждение секрета без раскрытия

1. Перечисляй файлы через Git, а не по всему рабочему каталогу. Нетрекнутые локальные
   `.env` не трогай, кроме проверки, не попали ли они в трекинг.
2. Ищи значения, похожие на токены, строки подключения, присваивания секретов.
   Сохраняй только:
   - путь и номер строки;
   - класс секрета;
   - плейсхолдер это/фикстура или нет;
   - булев результат сравнения с рабочим значением.
3. Никогда не печатай, не хэшируй, не маскируй частично и не копируй значение в вывод
   или доказательства. Даже хэш может стать устойчивым коррелятором.
4. Если строка из репозитория может быть фикстурой — сравнивай в памяти:
   - строка == CI/тестовая фикстура;
   - строка == рабочий секрет из конфигурации.
5. Строка в коде, равная рабочему секрету, — подтверждённый инцидент. Сначала ротация/отзыв,
   потом чистка исходников и истории. Удалить строку — это ещё не починка.
6. После записи отчётов рекурсивно просканируй папку доказательств на строки, похожие
   на секреты, и требуй нуля совпадений.

Минимальная форма доказательства:

```json
{
  "file": "path/to/source.ts",
  "line": 12,
  "kind": "api_token",
  "equalsTestFixture": false,
  "equalsConfiguredProduction": true
}
```

## Read-only проверки production

- До проверок озвучь запрещённое: никаких записей, создания аккаунтов, брутфорса,
  валидации токенов, изменения вебхуков, вредоносных загрузок.
- Максимум одна заведомо неверная попытка авторизации, если нужна семантика ошибки.
  Записывай статус, тип контента и общую форму ответа — не данные и не полные тела.
- Для cookie сохраняй только имя и флаги (`HttpOnly`, `Secure`, `SameSite`, domain/path).
  Значения — никогда.
- Для CORS используй заведомо чужой origin и смотри заголовки allow-origin/credentials;
  не суди о защите по одному статусу.
- Для закрытых маршрутов проверь редирект/401 анонима и отдельно рабочий авторизованный
  доступ.
- Для БД начинай явную транзакцию `READ ONLY` и запрашивай только метаданные схемы и
  агрегаты. Не возвращай строки пользователей, URL БД, логины, строки подключения.
- Сохраняй доказательства структурно (JSON), потом перечитай их перед завершением.

## Как отличить находку от шума

- HTTP 200 с телом ошибки авторизации — слабость мониторинга/статусов, а не обход
  авторизации, если сессия не выдана.
- Прерванные prefetch-запросы — не сетевой сбой; отделяй `requestfailed` браузера от
  реальных 4xx/5xx.
- Запись в advisory ещё не значит Critical. Фиксируй установленную версию, прямая/транзитивная
  зависимость, достижимость в рантайме, включённый путь/плагин, версию с фиксом.
- Захардкоженный секрет, равный production, — Critical независимо от приватности репозитория.
- Тестовый/дев-логин — реальная поверхность авторизации. Проверяй включение в production,
  привилегии и изоляцию целевого аккаунта, энтропию кода, срок жизни, отзыв, лог, лимит
  попыток и семантику HTTP-статуса.
