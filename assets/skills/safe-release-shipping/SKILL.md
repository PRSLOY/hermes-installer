# Безопасная публикация релиза

## Когда использовать

Безопасно закоммитить, опубликовать и задеплоить релиз, не затащив в него лишних локальных изменений и не запушив не ту ветку. Срабатывает на «закоммить и запушь», «выложи релиз», «задеплой», «в проде должен быть точный коммит», когда дерево грязное или ветки разошлись. Не срабатывает на обычные правки кода без публикации.


Для задач, которые заканчиваются коммитом/пушем/деплоем — особенно когда чекаут грязный,
текущая ветка может быть не `main`, продакшен должен соответствовать точному коммиту или
история могла разойтись.

Коммит, пуш и деплой — действия, меняющие общий/удалённый ресурс. Делай их только когда
человек об этом попросил. Ничего не удаляй и не переписывай из чужой работы без явной просьбы.

## Инварианты релиза

1. **Никогда не угадывай ветку назначения.** Прочитай `git branch --show-current`,
   remotes и расхождение веток до пуша.
2. **Стейджь явные пути.** Не используй `git add .`, когда есть несвязанные файлы.
3. **Проверь staged-артефакт.** `git diff --cached --check`, `git diff --cached --stat` и
   просмотр staged-диффа, а не всего грязного чекаута.
4. **Не форсируй неожиданный граф.** Если пуш отклонён или `HEAD...origin/main` разошлись —
   сначала fetch и осмотри граф, потом rebase/merge/cherry-pick.
5. **Деплой точного SHA из чистого дерева.** Успешная локальная сборка из грязного чекаута
   не доказывает, что задеплоенный артефакт содержит только нужный коммит.
6. **Проверь снаружи после деплоя.** Статуса провайдера недостаточно; дёрни публичный
   health-эндпоинт и хотя бы один пользовательский маршрут.
7. **Сохрани работу человека.** Никогда не stash/удаляй/стейджь/переписывай несвязанные
   локальные файлы без явной просьбы.

## Порядок работы

### 1. Узнай состояние репозитория

```bash
git status --short
git branch --show-current
git log -3 --oneline --decorate
git remote -v
```

До выбора ветки:

```bash
git fetch origin --prune
git rev-list --left-right --count HEAD...origin/main
git log --graph --oneline --decorate --all -12
```

Если текущая ветка — фича-ветка, по умолчанию публикуй её:

```bash
git push -u origin HEAD
```

**Не** пиши `git push origin main`, пока не подтверждено, что `HEAD` — задуманный коммит `main`.

### 2. Стейдж только нужных файлов

```bash
git add -- path/to/file1 path/to/file2
git diff --cached --check
git status --short
git diff --cached --stat
```

Сначала точечные тесты, потом полные тесты/typecheck/lint/build. Держи скрипты, меняющие
продакшен, вне обычной проверки, если задача явно не требует; предпочитай dry-run.

Для релизов безопасности зависимостей не приравнивай нулевой `npm audit` к безопасному
артефакту. Обновляй прямых владельцев явно, избегай `npm audit fix --force`, проверь
резолвнутое дерево, требуй чистый **обычный `npm ci` без спецфлагов** до отгрузки. См.
`references/npm-security-upgrades.md`.

### 3. Просмотри реальный дифф релиза

Просмотри `git diff --cached`. При желании можно отдать staged-дифф на независимое ревью
внешней моделью/ревьюером, если такой канал настроен, — но это опция, а не обязательный
шаг, и конкретной встроенной команды для этого здесь нет.

### 4. Коммит и безопасная публикация

```bash
git commit -m "fix: короткое описание"
git push -u origin HEAD
LOCAL_SHA=$(git rev-parse HEAD)
REMOTE_SHA=$(git ls-remote origin "refs/heads/$(git branch --show-current)" | cut -f1)
test "$LOCAL_SHA" = "$REMOTE_SHA"
```

Если пуш падает:

- Сеть/транзиент: ретрай, затем проверь удалённый SHA.
- Non-fast-forward: fetch и осмотр истории. Не форс-пушь рефлекторно.
- Разошедшийся `main`: сравни деревья и merge-родителей до cherry-pick. Merge PR может
  сохранить историю, разрешив конкретные файлы как удалённые.

### 5. Деплой точного SHA из чистого worktree

Создай detached worktree на опубликованном SHA, вне основного чекаута:

```bash
SHA=$(git rev-parse HEAD)
DEPLOY_DIR="/absolute/path/deploy-${SHA:0:8}"
git worktree add --detach "$DEPLOY_DIR" "$SHA"
```

Для Vercel скопируй/воссоздай только `.vercel/project.json` в deploy-worktree, затем
деплой из этого каталога:

```bash
cd "$DEPLOY_DIR"
npx vercel deploy --prod --yes
```

Не копируй `.env`, если локальные переменные действительно не нужны; предпочитай
переменные окружения продакшена на стороне провайдера.

### 6. Проверка и уборка

Подтверди: статус деплоя Ready/успешен; продакшен-alias указывает на новый деплой;
публичный health-эндпоинт возвращает ожидаемое тело и 2xx; главный маршрут возвращает 2xx;
опубликованный удалённый SHA равен задеплоенному SHA worktree.

Затем удали только временный worktree:

```bash
git worktree remove --force "$DEPLOY_DIR"
```

Если Windows снял регистрацию worktree, но оставил каталог из-за транзиентного лока —
убедись, что его нет в `git worktree list`, и удали этот конкретный временный каталог
после выхода деплоящего процесса.

## Windows/MSYS

- Терминал может гонять Bash через MSYS, а нативные инструменты — Windows-исполняемые.
- Для `git worktree` предпочитай нативные абсолютные пути (`D:/project-deploy-abc123`);
  `/d/...` может неожиданно ремапиться.
- Нативный `curl.exe` может не понимать MSYS `/tmp` или `/dev/null`. Для маленьких JSON-тел
  используй прямой stdout, а `-o NUL` — для сброса вывода.

## Когда остановиться и осмотреться

- Текущая ветка и задуманная удалённая цель различаются.
- Cherry-pick сообщает о конфликтах modify/delete.
- В `main` нет файлов, присутствующих в задеплоенной фича-ветке.
- Источник деплоя содержит несвязанные грязные/нетрекнутые файлы.
- Провайдер Ready, но публичные HTTP-проверки падают.

См. `references/git-divergence-and-exact-sha-vercel.md` — сжатый паттерн инцидента и дерево
решений.
