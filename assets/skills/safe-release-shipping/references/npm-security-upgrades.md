# Апгрейды безопасности npm внутри релиза

Когда уязвимости зависимостей нужно починить, не превращая релиз в неконтролируемый
мажорный апгрейд.

## Инварианты

- `npm audit` — свидетельство уязвимостей, а не план ремонта пакетного менеджера.
- Никогда не используй `npm audit fix --force` в релизной ветке. Он может понизить прямые
  пакеты или пересечь границы мажорных версий.
- Ноль в audit недостаточен. Должны пройти также дерево зависимостей, чистая установка,
  тесты проекта и продакшен-сборка.
- Держи ремонт зависимостей в отдельном коммите/релизе, когда это практично.

## Минимальный workflow

1. Сними текущий отчёт и владельцев:

   ```bash
   npm audit --json
   npm explain <vulnerable-package>
   npm outdated --json
   ```

2. Обнови уязвимые **прямые** пакеты явно до наименьших исправленных версий. Не делай
   сначала слепой общий апдейт.
3. Для транзитивных находок предпочитай по порядку:
   - patch/minor апдейт прямого владельца;
   - узкий `overrides` на одну дочернюю зависимость, после проверки совместимости API;
   - замена/удаление прямого владельца, если исправленного upstream нет.
4. Если повторные install/audit дают противоречивое или невалидное дерево lock — прекрати
   наслаивать фиксы. Восстанови файлы пакета, примени финальные версии один раз, удали
   `node_modules` и lockfile, сгенерируй свежий lockfile, просмотри дифф.
5. Прогони все гейты:

   ```bash
   npm audit --audit-level=low
   npm ls --omit=optional --all --parseable > /dev/null
   rm -rf node_modules
   npm ci
   npm test
   npm run typecheck
   npm run lint
   npm run build
   ```

   Используй реальные скрипты репозитория, если имена другие.

## Ловушки резолва peer'ов

### Опциональные framework-пиры

Пакет может объявлять адаптеры для фреймворков, которые приложение не использует. npm может
всё равно пытаться резолвить эти опциональные peer'ы и рапортовать конфликт.

- Не ставь неиспользуемый фреймворк, чтобы заткнуть npm.
- Не хватайся сразу за `--force`.
- Сначала обнови реальную peer-цепочку приложения до совместимых версий.
- `--legacy-peer-deps` можно использовать для построения lockfile, когда конфликт — только
  неиспользуемый опциональный адаптер, но финальный lockfile обязан пройти обычный `npm ci`
  без этого флага до отгрузки.

### Хойстинг несовместимых `0.x`-диапазонов

Инструменты вроде Vite, esbuild, миграционных CLI могут требовать несовместимые `0.x`.
Валидное дерево обычно держит одну версию в корне и другую вложенной под её владельцем.

- Инспектируй через `npm explain` и `npm ls <package> --all`.
- Пинь прямую корневую версию только когда реальный корневой peer требует.
- Узкий child-override — только когда старый потребитель проверен с исправленной дочерней.
- Проверь затронутый CLI напрямую после override, не только тесты приложения.

### Кросс-платформенные опциональные пакеты

На Windows npm может помечать чужеплатформенные опциональные WASM/native пакеты как пустые,
лишние или невалидные, хотя устанавливаемое неопциональное дерево здорово.

- Диагностируй точные записи до их игнорирования.
- Не добавляй внутренние опциональные runtime-пакеты как прямые зависимости ради `npm ls`.
- Используй `npm ls --omit=optional` как гейт только после подтверждения, что все остатки
  действительно платформенно-опциональны. Обычный `npm ci` и сборка/деплой на целевой
  платформе всё равно должны пройти.

## Дрейф линта и тулчейна

Чистая регенерация lockfile может подтянуть новый lint-плагин в допустимом диапазоне и
превратить ранее принятый код в ошибки.

- Сравни версию плагина с последним проверенным lockfile.
- Если плагин не связан с находкой безопасности — пинь ранее проверенную версию, а не
  отключай правила и не рефактори runtime-код внутри релиза только про безопасность.
- Запиши апгрейд линта как отдельную работу, если новые правила желательны.

## Сборки, требующие переменных окружения

Чистый worktree может упасть на import-time валидации окружения, даже если компиляция верна.

- Не копируй продакшен-секреты в worktree ради сборки.
- Если код сборки только валидирует синтаксис — дай заведомо фейковые синтаксически валидные
  значения и недостижимый локальный эндпоинт БД.
- Никогда так не делай, когда сборка читает/пишет БД или имеет внешние side-effect'ы;
  используй изолированное preview-окружение провайдера.
- Деплой провайдера с точного SHA остаётся авторитетной проверкой сборки на платформе.

## Доказательства завершения

До коммита/пуша зафиксируй: изменённые прямые версии и каждый override с обоснованием;
результат `npm audit`; результат дерева зависимостей; результат обычного `npm ci`; тесты,
typecheck, lint, проверки миграций/CLI и сборку; точный SHA коммита и внешние пробы деплоя.
