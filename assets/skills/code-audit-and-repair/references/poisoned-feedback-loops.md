# Отравленные циклы обратной связи

Repro-цикл — доказательство, только если ты проверил, что он реально исполняет. Непроверенный
цикл уверенно доложит о не том коде, и ты потратишь часы на несуществующий дефект.

Самая дорогая ловушка в аудите. Читай это до любой находки, что примитив, блокировка или
низкоуровневый механизм сломан.

## Признак

> «Примитив идеально работает в изоляции, но падает при использовании из проекта».

Этот зазор почти никогда не вина проекта. Почти всегда — загрязнённое окружение импортов.
Считай эту фразу триггером остановиться и проверить цикл.

## Затенение — доминирующая причина

Python резолвит импорты по `sys.path` по порядку, каталог скрипта добавляется в начало.
Любой файл в рабочем каталоге, названный как импортируемый модуль, молча его заменит.

Реальный случай: трёхстрочная заглушка `fcntl.py` (`LOCK_EX = 1`, `flock()` → `None`)
лежала в каталоге черновиков теста. Продакшен-код делал `try: import fcntl / except ImportError:`
для выбора POSIX/Windows ветки. Заглушка делала `try` успешным — код брал POSIX-ветку на
Windows, и блокировка становилась no-op. Замер: 5 процессов × 40 неатомарных инкрементов
дали 20 вместо 200, конкурентные писатели портили файл.

Отдельно тот же `fcntl.flock` блокировал корректно — потому что у отдельного скрипта
заглушки не было на пути. Два противоречивых вердикта, оба «замерены», с одной машины.

## Проверь цикл до доверия

Смотри загруженный артефакт напрямую, а не выводи из поведения:

```python
import importlib, inspect
mod = importlib.import_module("the_module")
print(mod.__file__)                               # это файл, который я правил?
print(inspect.getsource(mod.the_function))        # это код, который я писал?
print(hasattr(mod, "shadowing_candidate"))        # не импортнулась ли заглушка?
```

`inspect.getsource` — решающая проба: печатает твой код — загружен нужный модуль; печатает
не твоё — нашёл затенение.

Если `getsource` показывает твой код, а обычный `import` нижележащего модуля падает — эта
комбинация сама доказывает затенение.

## Другие загрязнители цикла

- **Устаревший bytecode.** Убедись, что запускаешь файл, который правил; чисти `__pycache__`,
  когда поведение противоречит исходнику.
- **Кросс-прогонное сравнение.** Сравнение прогона из одного окружения с прогоном из
  другого впитывает дрейф окружения. Сравнивай в одном процессе, одном интерпретаторе,
  на одном входе — см. `differential-old-vs-new-proof.md`.
- **Re-exec при spawn.** На Windows `multiprocessing` использует spawn и заново исполняет
  модуль в каждом ребёнке. Побочные эффекты уровня модуля (удаление фикстур, запись
  setup-файлов) идут раз на ребёнка и тихо инвалидируют тест. Убери весь setup за
  `__main__`-guard, конфигурацию передавай явными аргументами, не глобалами.
- **Глобалы не доезжают до spawn-детей.** Передавай режим аргументом, иначе ребёнок молча
  тестирует не тот вариант.
- **Самозагрязнение стенда.** Если тестируемый код читает переменную окружения только при
  импорте, а стенд ставит её после импорта — задуманная ветка не исполнится.

## Дисциплина

- Держи каталоги черновиков свободными от файлов, названных как модули. Никогда не оставляй
  удобную заглушку с именем stdlib-модуля.
- Любой вердикт про конкурентность/блокировки прогоняй на чистом окружении до отчёта.
- Находки по конкурентности повторяй минимум трижды. Противоречивые одиночные прогоны —
  подпись загрязнённого цикла, а не флаки-продукта.
- Вердикт из сломанного цикла — отзови громко, перепроверь на чистом, назови загрязнитель
  в отчёте.
