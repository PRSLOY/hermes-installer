# Ловушки запуска локального сервиса

Статический аудит может быть чист, а приложение всё равно соврёт в момент запуска. Эти
runtime-ловушки маскируют реальное состояние и порождают ложные находки в обе стороны
(рабочую сборку сочтут сломанной, сломанную — чистой).

## 1. Два сервера на одном порту; отвечает устаревший

На Windows привязка к уже занятому слушающему порту не всегда надёжно отклоняется. Запусти
сервер дважды — **оба** могут отрапортовать `listening`, при этом старый процесс всё ещё
обслуживает запросы. Тогда все симптомы идут от старого кода: неизменные ответы после
правки, эндпоинты 404-ят, хотя обработчик есть в файле, который ты только что запустил.

Случай с 404 самый обманчивый: обработчик есть, маршруты выглядят зарегистрированными, а
он всё равно 404-ит — потому что отвечает не твой процесс.

Диагностируй до правки кода:

```bash
# кто реально слушает порт
netstat -ano | grep ':8765' | grep -i listen

# и что это за PID
for pid in $(netstat -ano | grep ':8765' | grep -i listen | awk '{print $5}' | sort -u); do
  taskkill /F /PID $pid
done
```

Исключи (или подтверди) устаревший слушатель *до* находки «маршрут пропал» / «правка не
подействовала». Убей все PID на порту, запусти ровно один экземпляр, перепроверь.

Следствие для фикса: если приложение имеет лаунчер — пусть отказывается стартовать второй
экземпляр или берёт лок на порт и выходит с понятным сообщением.

## 2. Credentials приходят из файла профиля, не из окружения

Не делай вывод «аккаунт не настроен» из-за отсутствия `keys.json` / env-переменных. Читай
загрузчик. В этом классе репозиториев профиль собирается из локального нетрекнутого файла
(`.env`, `keys.json`, хранилище аккаунтов), который приложение читает на старте.

Проверяй возможность, спрашивая работающее приложение, а не grep'ая ФС:

```bash
curl -s http://127.0.0.1:8765/api/accounts
```

Поля вроде `has_password: true` / `has_totp: true` доказывают загрузку профиля без раскрытия
значений. Флаги наличия — безопасное свидетельство.

Подтверди, что хранилище секретов реально игнорируется:

```bash
git check-ignore -v .env state_1.json
```

## 3. Захардкоженная зависимость без проверки живости

Прокси/эндпоинт, безусловно переданный браузеру или клиенту, становится мёртвой фичей в
момент, когда зависимость не запущена: запуск падает или тихо деградирует в несвязанную
ошибку, читающуюся как баг твоей правки.

Паттерн: лаунчер всегда форвардил `socks5://127.0.0.1:9090`, локальный форвардер не был
запущен — автоматизация браузера не могла подключиться.

Фикс: пробуй до использования и делай fallback.

```python
def proxy_alive(url):
    if not url:
        return False
    try:
        host, port = url.rsplit("://", 1)[-1].rsplit(":", 1)
        with socket.create_connection((host, int(port)), timeout=1):
            return True
    except (OSError, ValueError):
        return False
```

Прикрепляй прокси только при прохождении пробы и логируй выбранный путь. Тест на обе ветки;
ветка «недоступно» — та, что была сломана.

## 4. Cookie-jar — это учётные данные

Файл `storage_state` Playwright/Puppeteer (и всё вроде `*_state.json`) содержит cookie
сессии, аутентифицирующие как аккаунт без пароля и без 2FA. Обращайся как с приватными ключами:

- gitignore'ь до генерации любого из них;
- никогда не прикрепляй к отчёту, диффу или тесту;
- при утечке единственное лекарство — ротация (разлогинить все сессии); удаления файла мало.

## 5. Живой логин за VPN / ограниченной сетью

Когда сетевой путь неочевиден (корпоративный прокси, доступ только по VPN, гео-ограничение),
автоматический логин в браузере — не чистый программный тест: он проверяет и сетевой путь.
Записывай, по какому пути шёл тест, и сообщай сбой связности как сбой связности — никогда
как «код логина сломан». Одно ручное подтверждение через сессию человека стоит больше, чем
повторные скриптовые попытки, которые не различают эти два случая.
